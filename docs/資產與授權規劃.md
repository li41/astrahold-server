# 星壘 — 資產與授權規劃

本文件讓 Server repository 內可以直接看懂目前資產策略與授權邊界；原始 license、provenance、manifest、Three.js mapping 與 QA 證據仍以 `li41/astrahold-assets` 為 source of truth。

Server 不保存 Client asset path，也不使用 asset path 決定 gameplay。

## 一、目前 repository 邊界

正式 repositories：

- Server：`li41/astrahold-server`
- Client：`li41/astrahold-client-three.js`
- Assets / 資產工具：`li41/astrahold-assets`

`li41/astrahold-tools` 已退役；原資產 preview / metadata / GLB validation 工具已併入 `astrahold-assets/tools/`。

不要再把 `astrahold-tools` 寫成正式獨立 repository。

## 二、Assets repository 的責任

`astrahold-assets` 保存：

- 資產候選與 catalog
- provenance
- license / attribution
- machine-readable manifest
- Three.js presentation mapping
- GLB / metadata QA
- asset preview / validation tooling
- 只有 Client 真正需要時才加入的 approved payload

Server 不讀取這些 presentation/build 資料。

## 三、目前資產狀態

截至目前 Assets 主線的有效資訊：

- active Client 是 Three.js。
- repository 主要保留 metadata、來源、授權、候選與規劃。
- 大型 binary payload 不因「已經買了／已在 library」就自動放進 repository。
- Client 真正需要某個資產時才重新匯入 approved payload。
- Unreal mapping 只保留 legacy / provenance 意義，不再是 current Client acceptance gate。

## 四、目前已盤點的資產類型

### 環境

目前有候選／來源紀錄的方向包含：

- 中世紀城堡
- 村莊／城鎮模組
- 城牆／塔樓
- Emberwatch 原創營地件
- 圍籬
- 帳篷
- 補給堆
- 燈籠／火炬
- rocks / vegetation / ground 類素材

Server 只關心它們是否對應需要 gameplay representation 的 collision / LOS / spawn / objective；不關心 Client 檔案路徑。

### 角色與怪物

目前保留角色／怪物 presentation 規格與候選來源。

Server 只使用 stable gameplay identity，例如：

- `ArchetypeID`
- `EntityID`

Client 再把這些 ID 映射到 approved model / animation。

### 道具與裝備

Assets 可以保存裝備模型、icon、material、hand socket 等 presentation mapping。

Server 保存的是：

- `ItemArchetypeID`
- slot legality
- damage / defense / block / resource effect
- weight
- class / level / policy eligibility
- inventory / equipment ownership

兩者不能混在一起。

### 音效

原始 Assets 規劃包含 combat、monster、loot、UI、campfire 等音效需求。

採用原則：

- license 明確
- raw redistribution 限制明確
- presentation-only
- Server event / state 可以觸發音效，但音效不能決定 gameplay

## 五、授權安全

### 必須保留的證據

第三方資產至少需要：

- 來源
- license class
- attribution 要求
- raw redistribution 限制
- commercial use eligibility
- 必要時保留原始 license 文件／supplier notice

這些證據留在 `astrahold-assets`，不要複製成 Server gameplay data。

### 常見處理原則

- Fab Standard：可作專案內容使用，但不要把 raw asset 當獨立素材重新散布。
- CC-BY：保留 attribution。
- CC0：可作為低風險 fallback，但仍要記錄來源。
- 其他 site-specific royalty-free：逐項確認，不因「免費下載」就當成可自由散布。
- Unreal-only / engine-only license：若正式 Client 不是該 engine，就不能當 current Three.js shipping dependency。

## 六、購買策略

維持 **$0-first**：

```text
先用已有合法素材 / Astrahold 原創素材
-> 證明 gameplay presentation pipeline
-> 確認真正瓶頸
-> 才購買能明確降低瓶頸的資產
```

不要把資產候選清單當 shopping list。

目前較合理的付費判斷順序：

1. 怪物若免費／已有素材在 animation / silhouette / quality 上仍是明確瓶頸，再購買。
2. 場景 kit 若組裝時間或一致性成為明確瓶頸，再購買。
3. Player final identity 在整體場景／戰鬥 feedback 還沒成熟前，不優先燒預算。

## 七、Three.js 資產接受原則

進正式 Client 前應至少確認：

- 模型可正常載入。
- animation clips 符合實際 gameplay presentation 需求。
- scale / orientation 正確。
- material / texture 不造成不可接受的 draw / memory cost。
- 大型場景可裁切、分區或做 LOD / level-of-detail。
- license / provenance 完整。
- stable gameplay ID mapping 明確。

這些是 Client / Assets 責任，不是 Server gameplay authority。

## 八、Server 與 Assets 的唯一合法連接

```text
Server stable ID / authoritative state
-> Protocol state / event
-> Client presentation mapping
-> approved asset
```

禁止：

```text
Server
-> Client model path
-> 用 mesh / animation 決定 gameplay
```

Server source 與 persistence 都不保存 Client model / texture / animation / icon path。
