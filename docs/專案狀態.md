## Client handoff

Server -> Client 的正式協作紀錄仍走：

`li41/astrahold-client-three.js` Issue #7

v24 Client consumption 要點：

- Protocol fence 升到 v24。
- `CombatEvent` 新增 `blocked: bool`。
- `CombatEvent.damage` 直接顯示 Server final mitigated damage。
- Client 不擲 block、不重算 PhysicalDefense / BlockReduction / MagicReduction。
- `blocked=true` 只用於盾牌 animation / VFX / SFX / UI feedback。
- Client 不自行新增 8 件裝備的取得方式。

PR #151 threat 是純 Server AI semantics，沒有新增 Client DTO / message，因此不需要額外 Protocol handoff。

Server 不修改 Client source。

## 目前內容討論狀態

### 盾牌 v1 已定案並完成 Server exact-head 驗證

- `PhysicalDefense / (PhysicalDefense + 20)`

- 一般成立正傷害最低 1
- 詳細三盾數值與平均減傷見 [遊戲內容與系統規劃](遊戲內容與系統規劃.md)

### Threat v1 已定案並完成 Server exact-head 驗證

- 初始 proximity acquisition 不等於永久 threat
- actual damage 直接累加 threat
- highest threat 決定 target
- invalid target prune + next-highest fallback
- disconnect ghost entity 不可維持 AI target legality
- evade / lifecycle reset 清 threat
- threat 不與 loot contribution 混成同一張表

### 吸魔武器已確認方向

- 不固定 +5 MP
- 不可無限吸同一目標
- 應與目標 MP／可吸額度相關
- 數值需有隨機變化

完整公式、取得方式、武器內容仍未定。

## Validation debt

部分 historical production E2E 仍可能包含舊 Protocol / 舊 Client assumptions。

PR #151 exact head 上的 production recovery / trusted-proxy / TLS / playable-siege 等既有紅燈，已與 exact base `00413e33997e6537da141e7b04e3ce01a7a66adb` 同型比較；base 已有相同 failure family。Server CI 與 Siege Load Lab 在 base / feature head 都 PASS，因此目前標記為 pre-existing validation debt，沒有證據顯示是 threat slice 新增 regression。

處理原則：

- 不隱藏紅燈。
- feature head 與 exact base head 做同型比較。
- base 已失敗才標記 pre-existing debt。
- 新 regression 不得以歷史債務為理由忽略。
- 真的影響 gameplay authority、data integrity、security、persistence correctness 的 failure 必須阻擋。

驗證規則見 [驗證規範](驗證規範.md)。
