# Astrahold Starfire Fire Bolt — Protocol v26 Additive Gameplay Contract

## Status

This slice adds the first Server-authoritative Starfire Mage combat action without changing the Protocol v26 wire shape.

The existing v26 `CharacterClassResourceState` message remains generic and now carries Star Heat as another stable class-resource vocabulary value.

## Canonical action

ActionID:

```text
starfire-fire-bolt
```

Server-authored V1 vertical-slice values:

- required ClassID: `class_starfire_mage`
- target: entity
- current Server combat range: 12 meters
- magic base damage: 90 (`D90` class-balance baseline)
- cooldown / cast cadence: 1.25 seconds
- accepted Server execution: `star_heat +8`, clamped to 100

The class-balance baseline fixes `D90 / 1.25s / +8 Star Heat` for Fire Bolt. It does not fix one production meter value for this action. The 12 meter value is therefore an explicit vertical-slice Server range aligned with the existing ranged combat envelope; it is not claimed as final balance canon.

A request rejected for wrong class, cooldown, invalid target, out-of-range legality, defeated actor, or another pre-execution legality failure does not increase Star Heat.

## Star Heat

Stable class-resource ID:

```text
star_heat
```

Runtime range:

```text
0..100
```

The current design vocabulary divides Star Heat into these bands:

- 0..39: low
- 40..69: medium
- 70..89: high
- 90..100: overheat

These bands are design vocabulary only in this slice. No additional high-heat damage bonus, cast lock, forced cooldown, decay, self-damage, or overheat penalty is invented here. Those outcomes require a separate Server-owned heat policy before gameplay depends on them.

Star Heat follows the same ownership policy as the other v26 class resources:

- mutable truth lives in `character.Service` on the world-owner path;
- it is combat-incarnation runtime state;
- it is intentionally not stored in the durable character snapshot yet;
- a trusted durable Starfire Mage join/reconnect reconstructs it from authoritative `ClassID` as `0/100`.

## Accepted-action resource semantics

Star Heat is intentionally different from Resolve, Momentum, and Hunt Momentum.

- Oathguard, Breaker, and Ranger V1 resource gains are conditioned on a successful Server-resolved hit.
- Fire Bolt's `+8 Star Heat` represents heat generated by executing the spell, so it is conditioned on an accepted Server execution rather than on target damage success.

The Server keeps these as distinct policy fields. Client animation, projectile VFX, local hit tests, cached cooldown state, or UI events never create Star Heat.

## Protocol compatibility

Protocol version remains:

```text
26
```

No new message type or field is added.

The existing Server -> Client reliable message remains:

```text
117 CharacterClassResourceState
```

Starfire example:

```json
{
  "entity_id": 42,
  "resource_id": "star_heat",
  "current": 8,
  "max": 100
}
```

The Client must replace presentation state with the received complete value. It must not increment Star Heat locally.

`ActionRejected.reason = wrong_class` remains the authoritative rejection when a non-Starfire character requests `starfire-fire-bolt`.

## Initial class lifecycle

For a trusted durable initial Starfire Mage selection, the authoritative publish order remains:

1. `CharacterClassState(class_starfire_mage)`
2. `CharacterClassResourceState(star_heat 0/100)`
3. correlated `InitialClassSelectionResult(committed)`

No live ClassID or Star Heat resource exists before the durability gate completes.

Reliable backpressure may delay these messages, but retrying presentation must not rerun persistence or gameplay mutation.

## Authority flow

```text
ClientUseAction intent
-> world-owner ClassID / target / range / cooldown validation
-> Server accepts and resolves Fire Bolt
-> authoritative damage / HP outcome and Star Heat +8
-> CharacterClassResourceState(updated full state)
-> authoritative action / combat events
```

The slice does not define a new externally observable ordering guarantee between the resource update and combat-event presentation beyond the existing reliable/message-channel semantics. Clients must consume each authoritative message as state or presentation feedback, not reconstruct gameplay outcome from local timing.

ClassID, range legality, action acceptance, damage, cooldown and Star Heat are Server decisions.

## Client boundary

The formal Client may expose `starfire-fire-bolt`, present `star_heat`, and derive presentation-only heat-band styling from the authoritative complete value. It must not infer permission, range legality, damage, cooldown, Star Heat mutation, overheat blocking, penalties, bonuses, or decay from animation, raycast, projectile visuals, equipment, UI state, or cached ClassID.
