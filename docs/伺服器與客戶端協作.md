# 星壘 — Server 與 Client 協作

本文件定義 **gpt-server ↔ gpt-client** 的長期協作方式。Current Protocol、active integration Issue、branch、SHA、blocker 與 rollout 狀態放 [專案狀態](專案狀態.md)；工作分類放 [待辦與待討論](待辦與待討論.md)。

## Agent identity

- Server agent：**gpt-server**
- Client agent：**gpt-client**

正式 repositories：

- Server：`li41/astrahold-server`
- Client：`li41/astrahold-client-three.js`

雙方不建立第二套正式 gameplay authority。

## 固定 authority 邊界

```text
Client Intent
-> Go Server Validate / Decide
-> Authoritative State / Events
-> Client Presentation
```

Server 是唯一 gameplay truth。Client animation、VFX、UI、camera、prediction、root motion、raycast、smoothing 不得決定 gameplay outcome。

## 寫入邊界

### gpt-server

可直接修改：

- `li41/astrahold-server`

只讀：

- `li41/astrahold-client-three.js`

若需要 Client 變更、Client 驗證、Protocol consumption、presentation integration 或需要 gpt-client 注意某件事，一律到 Client repository 建 `[gpt-server]` Issue 或在既有相關 Issue 留 comment。

不要直接改 Client source。

### gpt-client

可直接修改 Client repository。Server repository 對 gpt-client 為只讀；需要 Server semantics／contract 變更時透過 GitHub Issue 提出，不直接改 Server source。

## 正式協作入口

Server -> Client 的正式協作入口是 Client repository GitHub Issue。

Issue title 建議：

```text
[gpt-server] <short integration topic>
```

內容至少包含：

- 玩家可見目標
- authoritative semantics
- affected message／field／event／state
- Protocol compatibility impact
- Server branch／exact commit
- Client 需要做的 decoder／presentation／runtime work
- Server 已完成的 validation
- 尚未完成、需要 Client runtime 驗證的部分

Issue／comment 是協作紀錄，不是第二份 gameplay contract。

## 地圖／場景協作邊界：Client-first

地圖與場景開發由正式 Three.js Client 主導；Server 不在 Client playable-space 之前先規劃地圖。

### Client 先做

由 Client 主導：

- map／scene layout
- 視覺動線與空間感
- environment／building／prop placement
- scene asset 組合
- playable-space 迭代
- camera／presentation 所需的場景調整

Client 可以用 scene node、visual collider、raycast 等方式完成呈現與設計迭代，但這些資料 **不會自動成為 gameplay authority**。

### 需要 gameplay authority 時回饋 Server

Client 做到一個具體 playable slice，發現需要 Server 決定結果時，再以 `[gpt-client]`／對應 integration Issue 或 comment handoff。典型需求包括：

- authoritative collision／traversability
- teleport／portal legality
- spawn／respawn point
- gameplay／interaction region
- AI navigation／encounter region 所需的 Server facts
- safe zone／combat zone
- siege gate／breach／capture legality
- 需要正式 Protocol state／event 的場景互動

Server 收到具體需求後，才把必要資料提升成穩定 gameplay ID／config／Protocol semantics，並以 tests 保護。

### Server 不先做

在沒有 Client handoff 前，gpt-server 不主動：

- 規劃下一張地圖
- 重做新手村 layout
- 規劃城牆／入口／portal／siege gate
- 決定 blocker 數量
- 決定 spawn layout
- 從 Client asset path／scene node／raycast 推導 gameplay collision 或 region

現有 Server world config 是目前既有 gameplay／compatibility truth，不代表未來 map roadmap。

## Source of truth

遇到衝突：

1. 使用者最新明確指示
2. 正式 Server source／Protocol contract
3. [專案狀態](專案狀態.md)
4. integration Issue／PR discussion
5. 歷史文件

Client 不從 Issue 猜 gameplay 規則；Server 不從 Client presentation implementation 反推 gameplay truth。

## Protocol handoff

若 Server 變更影響 wire contract：

1. Server 先完成 authoritative semantics。
2. 更新 codec／ingress／runtime／replication 與 compatibility tests。
3. Wire-incompatible 時升 Protocol fence。
4. 跑 exact-head Server validation。
5. gpt-server 在 Client repo Issue 附 exact Server SHA 與欄位語義。
6. gpt-client 自行完成 decoder／presentation／runtime integration。
7. meaningful checkpoint 再做兩端 runtime validation。

詳細規則見 [通訊協定同步](通訊協定同步.md)。

## Runtime 驗證邊界

Server tests 可以證明 Server gameplay correctness，但不能取代 Client presentation 驗收。

需要 Client runtime 驗證的典型項目：

- animation／facing presentation
- HUD／UI state
- interpolation／correction quality
- pickup／inventory feedback
- death／respawn UX
- equipment model／icon／MainHand／OffHand presentation
- skin／appearance mapping
- shield block animation／VFX／SFX
- map／scene playable-space presentation

反過來，Client 視覺驗收也不能取代 Server collision、combat、inventory、persistence、AI、teleport／region legality 等 authoritative tests。

## Worktree safety

- 同一 worktree 同時只能有一個 writer。
- gpt-server 不碰 Client local dirty／untracked／branch state。
- 不擅自 reset／stash／clean／restore／force overwrite／force push。
- 跨 repo coordination 優先 Issue，不直接代改對方 source。
