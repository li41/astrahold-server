# S4-F.4 — Formal Login / Session Credential Issuance

## Scope

S4-F.4 adds a bounded Server-side login and short-lived session credential issuance path on top of the credential contracts completed in S4-F.1 through S4-F.3.

The stage does **not** move account authentication into GameV1 and does not add Protocol v10. Instead, it adds a separate TLS 1.3 control-plane endpoint that authenticates a Server-owned account login record and returns one random opaque bearer credential. The game connection then submits that bearer through the existing `ASTRAH1` pre-GameV1 credential preface.

The dependency direction remains:

```text
TLS 1.3 login control plane
        ↓
Server account verifier
        ↓
short-lived opaque session credential issuer
        ↓
existing sessioncredential.Provider
        ↓
ASTRAH1 trusted game admission
        ↓
existing Session / Ownership Fence
        ↓
World Runtime
```

The login service never writes world state and never receives SessionID, EntityID, HP, position, team, winner, or any other gameplay authority.

## Why this stage exists

Before S4-F.4, production trusted authentication depended on an operator pre-provisioning the bearer that a Client later submitted in `ASTRAH1`.

S4-F.4 separates two different credentials:

1. an **account-login secret**, used only over the dedicated TLS login endpoint;
2. a **short-lived session credential**, generated by the Server after login and accepted by the existing trusted game admission path.

The Client-visible session bearer contains no CharacterID, takeover bit, expiry timestamp, revocation scope, or signed gameplay claims. Those values stay Server-owned.

## Production modes

`worldd` now has two mutually exclusive trusted-auth modes.

### Existing static trusted-character mode

```text
-trusted-character-auth-file
```

This remains the S4-F.1/S4-F.2/S4-F.3 compatibility and operational mode.

### Issued-session login mode

All of the following must be configured together:

```text
-session-login-account-file
-session-login-tls-listen
-session-login-tls-cert
-session-login-tls-key
-session-credential-ttl
```

`-session-credential-ttl` defaults to 15 minutes and is bounded to 1 minute through 24 hours.

Issued-session mode and `-trusted-character-auth-file` are deliberately mutually exclusive. This keeps one authoritative credential namespace and one revocation-scope set per `worldd` process.

The trusted game TCP backend still has to be literal loopback. Production game clients should continue to reach it through the existing TLS 1.3 trusted game ingress.

## Reference account verifier

The first login verifier is intentionally small and file-backed so the issuance contract can be exercised without pretending that Astrahold already owns a complete account database or human-password service.

Schema:

```json
{
  "schema_version": 1,
  "revision": "accounts-001",
  "accounts": [
    {
      "login_id": "alice",
      "login_secret_sha256": "<64 lowercase hex characters>",
      "character_id": "alice-character",
      "allow_active_takeover": false
    }
  ]
}
```

Rules:

- strict JSON decode; unknown fields and trailing values fail startup;
- non-empty revision and at least one account are required;
- `login_id` is unique, trimmed, and at most 128 bytes;
- `login_secret_sha256` is exactly 32 bytes encoded as lowercase hex;
- CharacterID is validated as a trusted Server-owned identity;
- `allow_active_takeover` remains a Server-side claim;
- wrong login ID or secret returns the same generic authentication failure.

`login_secret_sha256` is intended for a **high-entropy account bootstrap secret**, not a human-memorable password. Plain SHA-256 is not a password KDF. A future human account system should use an external identity provider or a password-specific verifier/KDF behind the same login-to-Server-claims boundary.

## Login HTTP contract

The login listener is TLS 1.3 only.

Endpoint:

```text
POST /v1/session/login
Content-Type: application/json
```

Request:

```json
{
  "login_id": "alice",
  "login_secret": "<high-entropy account secret>"
}
```

Successful response:

```json
{
  "session_credential": "<opaque base64url bearer>",
  "expires_at": "2026-08-16T08:30:00Z"
}
```

The response uses `Cache-Control: no-store` and `Pragma: no-cache`.

The Client does **not** send a CharacterID in the login request. Unknown JSON fields are rejected, so a Client cannot add `character_id`, takeover permission, or other authority claims to the request.

## Issued bearer properties

Each session credential is generated from 32 bytes of `crypto/rand` entropy and encoded with unpadded base64url. The resulting bearer is 43 ASCII characters and fits comfortably inside the existing 256-byte `ASTRAH1` credential maximum.

The Server stores only:

- SHA-256 digest of the issued bearer;
- trusted CharacterID selected by the account verifier;
- optional active-takeover claim selected by the account verifier;
- exact expiry time;
- a Server-only revocation scope derived from the issued credential digest.

The plaintext session bearer is returned to the caller but is not retained in the provider map.

## Provider and transport publication ordering

S4-F.4 reuses the S4-F.3 transport allow-set instead of adding another revocation mechanism.

### Issuance

For a newly generated credential:

```text
generate random opaque bearer
        ↓
build next provider snapshot
        ↓
publish next active revocation-scope set
        ↓
publish next credential provider snapshot
        ↓
return bearer to login caller
```

The new scope is therefore allowed before the credential can resolve. The small handoff window is fail-closed: an unpublished bearer cannot authenticate.

### Revocation / logout / expiry

Removal uses the security-sensitive reverse ordering:

```text
build provider snapshot without retired credential
        ↓
replace transport active-scope set
        ↓
ready=false + remove realtime token/route for retired peer
        ↓
publish provider snapshot without retired credential
        ↓
existing closePeer / fenced Leave completion
```

This retains the S4-F.3 guarantee that a live game peer loses realtime authority before its revoked proof disappears from the credential provider.

## Explicit logout

Endpoint:

```text
POST /v1/session/logout
Authorization: Bearer <session_credential>
```

A known issued credential is removed from the provider and its revocation scope is removed from the transport allow-set. If that bearer currently owns a live game peer, the peer is retired through the existing transport teardown and fenced world-leave path.

Unknown-but-well-formed bearer values also return `204 No Content`; logout does not become a credential-existence oracle.

## Expiry

Issued credentials carry an exact Server-clock `ExpiresAt` boundary.

At the cutoff:

- `Provider.Resolve` rejects the bearer at the exact expiry time and afterward;
- the issuance runtime removes the expired credential from its next snapshot;
- the active transport scope set is recomputed;
- any live peer authenticated with the expired credential is retired through S4-F.3 semantics.

No Client clock participates.

Issuance/revocation changes wake the runtime boundary scheduler so the process does not need polling.

## Account login and active-session ownership

Account authentication selects the trusted CharacterID and optional `allow_active_takeover` claim before session credential issuance.

Multiple valid session credentials may be issued for the same CharacterID. That does **not** create multiple authoritative characters:

- normal duplicate active admission still fails closed;
- an issued credential with no takeover claim cannot displace an active owner;
- an issued credential with the Server-owned takeover claim still goes through the existing connection-scoped takeover authorizer, candidate gate, ownership fence, and CAS transfer;
- stale peer teardown cannot remove a newer owner.

The issuer is therefore a proof minting service, not an ownership service.

## TLS and request bounds

The login service:

- requires TLS 1.3 or newer;
- requires certificate and key files at process startup;
- caps JSON request bodies at 4096 bytes;
- caps login IDs at 128 bytes;
- caps login secrets at 256 bytes;
- uses bounded read/header/write/idle HTTP timeouts;
- never logs login secrets or issued bearer values.

TLS certificate reload remains restart-only in this stage.

## Restart behavior

Issued session credentials are intentionally process-local and are not persisted.

If `worldd` restarts:

- all game TCP/UDP sessions are already gone;
- all previously issued session bearers become invalid;
- clients must authenticate to the login endpoint again and obtain a new session credential;
- durable character state and castle ownership continue to use their existing persistence paths.

This avoids making short-lived authentication proof state a new durable gameplay authority.

## Protocol / realtime boundary

No game wire change is introduced:

- Protocol remains v9;
- `ASTRAH1` preface remains unchanged;
- MessageType values remain unchanged;
- `SessionWelcome` ordering remains unchanged;
- public 128-bit RoutingID and HMAC-SHA256/128 realtime authentication remain unchanged;
- UDP MTU remains 1200 bytes;
- GameV1 snapshot payload remains 1132 bytes / 43 entities;
- same-IP authenticated UDP source-port migration remains unchanged.

The login HTTP JSON contract is a separate TLS control plane, not a GameV1 message.

## Focused acceptance coverage

S4-F.4 adds tests for:

- issued-credential value contract;
- strict account login record validation;
- wrong account secret rejection;
- CharacterID and takeover authority selected only by Server account records;
- 32-byte random bearer generation and digest-only provider storage;
- transport scope publication before provider publication on issuance;
- transport scope removal before provider removal on logout/revocation;
- exact expiry cutoff and provider pruning;
- unknown Client authority fields rejected by the login JSON decoder;
- login followed by provider resolution through the same trusted game credential path;
- logout followed by provider rejection;
- real TLS 1.3 login service negotiation;
- mutual exclusion between issued-session mode and the legacy/static trusted credential file.

Full Server CI remains the merge gate: `go test ./...`, `go vet ./...`, and the concurrency race detector. Existing siege/load gates remain authoritative when triggered by the changed paths.

## Deliberate non-goals

S4-F.4 does not add:

- human username/password storage or password hashing/KDF;
- OAuth/OIDC/social login;
- account registration, email verification, MFA, password reset, or recovery;
- multi-character account selection;
- refresh tokens;
- durable or distributed session credential storage;
- cross-server revocation propagation;
- IP/device binding;
- rate-limit infrastructure shared across multiple login servers;
- TLS certificate hot reload;
- automatic Godot login UI/bootstrap integration;
- Client-visible structured kick/logout reason;
- Protocol v10;
- UDP encryption or cross-IP realtime migration.

A next bounded stage can integrate the Godot Client with this TLS login contract and/or replace the reference high-entropy account-secret verifier with a real account/identity backend without changing the game transport authority model.
