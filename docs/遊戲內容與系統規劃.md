# 星壘 — 遊戲內容與系統規劃

本文件只記錄**已討論確認的內容**、仍待討論的設計空缺，以及後續 Server gameplay roadmap。

任何武器、怪物、技能、掉落、商店、數值、經濟、取得方式，都不能因為「系統已經能做」就由 agent 自行補完。

## 一、內容設計原則

1. 先和使用者討論內容，再實作。
2. Server correctness 可以直接修，但內容數值與取得方式不得自行決定。
3. Gameplay feature 先做通用 module，再透過 archetype / stats / policy / loot table / AI config / respawn policy 擴充。
4. 不為單一怪物、單一 item、單一 map 複製 gameplay system。
5. Client 不決定 damage、loot、equipment legality、AI、HP/MP、cooldown 或 persistence outcome。

## 五、武器目前 Server 規則

PR #149 已實作：

- 只有 entity-target `basic-attack` 使用本批武器的 authored damage。
- Server 先驗證 target / range / LOS / resource / protection legality，再擲傷害。
- Client 不提供傷害值或隨機 roll。
- CombatEvent、HP mutation、loot contribution 使用同一份 Server actual damage truth。
- attack interval 沿用既有 combat cooldown authority，不新增第二套 cooldown system。

### 命中修正

`accuracy_modifier` 已有資料，但**公式尚未討論，所以目前不生效**。

## 六、盾牌防禦與格擋 v1

### 物理防禦公式

已定案：

```text
PhysicalMitigationRate = PhysicalDefense / (PhysicalDefense + 20)
```

因此目前三面盾的固定物理減傷為：

- `PhysicalDefense = 2`：約 9.09%
- `PhysicalDefense = 3`：約 13.04%
- `PhysicalDefense = 4`：約 16.67%

不使用 `RawDamage - PhysicalDefense` 的平減方式，避免在目前低階武器傷害區間中讓盾牌過度壓低傷害。

### Authoritative physical flow

```text
合法 Physical Damage
-> 讀取 DamageType / Blockable
-> 讀取受擊者 authoritative OffHand
-> 套 PhysicalDefense
-> 若 Blockable，Server 擲一次 BlockChance
-> 成功才套 BlockReduction
-> 中間保持精度
-> 最後四捨五入一次
-> 一般成立的正傷害最低 1
-> FinalDamage
-> HP mutation / CombatEvent / contribution
```

已鎖定：

- `DamageType` 與 `Blockable` 是兩個獨立 Server semantics。
- `Physical` **不代表一定可格擋**。
- `BlockChance` 只由 Server 擲。
- `BlockReduction` 只有格擋成功才套用。
- 同一筆 damage instance 最多一次格擋 roll。
- v1 不看角色面向、不看攻擊角度、不做背後繞盾判定。
- HP mutation、CombatEvent、loot contribution 使用同一份 authoritative final damage。
- Client 不得自行擲格擋、不重算防禦、不依模型或動畫推導結果。
- Client 只能根據 Server 回傳的 block result 播放盾牌動畫、VFX、SFX。

### v1 Blockable 規則

目前正式 action semantics：

- `basic-attack`：`Physical + Blockable`
- `wolf-bite`：`Physical + Blockable`
- `shatter-strike`：`Physical + NotBlockable`
- `fireball`：`Magic + NotBlockable`
- `meteor-strike`：`Magic + NotBlockable`

Point / ground AoE 不會因為最後命中 entity 就自動變成可格擋。DoT、環境、墜落、siege / gate 等其他 damage path 也不得因為是 Physical 就自動套盾牌 Block；未來要能格擋時必須由 Server damage semantics 明確標記。

### 魔法減傷

MagicReduction 與 Block 完全分離。

```text
FinalMagicDamage = RawMagicDamage * (1 - MagicReduction)
```

方紋魔盾 `MagicReduction = 8%`，所以目前對合法 Magic damage：

```text
RawMagicDamage * 0.92
```

Magic damage 不擲盾牌的 `BlockChance`。

### Rounding 與最低傷害

- mitigation pipeline 中間保持高精度。
- 最後只做一次一般四捨五入：例如 5.49 -> 5、5.50 -> 6。
- RawDamage > 0、且沒有明確 immunity / invulnerability / absorb result 時，FinalDamage 最低 1。
- 未來明確的免疫／無敵／完全吸收仍可合法產生 0 damage；不能用自然 rounding 到 0 取代這些 gameplay result。

### 格擋平均效果

長期平均值用來看平衡，不是每一擊固定減傷：

```text
AverageTotalReduction
= 1 - (1 - PhysicalMitigationRate) * (1 - BlockChance * BlockReduction)
```

因此目前約為：

- 木鐵圓盾：14.8%
- 守備盾：19.2%
- 方紋魔盾：10.2%

例如木鐵圓盾的 `8% x 25% = 2%` 代表格擋機制本身的長期平均額外效果約 2%，不是每一擊固定多減 2%。

### 職業限制

低階盾：**所有職業都能使用**。

裝備資格由 Server 驗證；Client 只能做 UI 提示。

正式資料模型：

```text
ClassPolicy = All
```

未來限制裝備使用：

```text
ClassPolicy = AllowList
AllowedClassIDs = [...stable ClassID...]
```

不要在 combat code 寫死「低品質必定全職業」。品質是內容分類；實際 equip legality 由 item archetype 的 policy 決定。

目前 durable character state 尚未建立正式 `ClassID`，因此現有低階裝備全部明確 authored 為 `All`；未來 `AllowList` 裝備在 Server 尚無 authoritative ClassID 時必須 fail closed。

### CombatEvent

盾牌 block 成功與否必須是 Server result。

Client-visible combat outcome 至少包含：

```text
final damage
blocked = true / false
```

`blocked=true` 只代表這次 Server 判定可格擋、完成唯一一次 BlockChance roll，且 roll 成功。Client 不得從盾牌裝備狀態自行推測或重擲。

## 七、怪物體型

Server `EntityState.BodySize` 是目前 authoritative body-size truth。

規則：

- 不從 Client scale 推測。
- 不從舊 entity incarnation 推測。
- 尚未討論的 monster archetype 不正式宣告 small / large。
- 未分類 monster 目前走 small compatibility damage table，只是 compatibility 行為，不代表內容上已定義成小型。

## 八、吸魔武器

PR #148 是技術原型，不是正式內容。

### 已撤回

- 固定 `+5 MP`
- `3 灰狼皮 -> 1 法杖`
- 任何因原型而自動成立的正式商店／掉落／兌換

### 已確認方向

- 吸取量不能固定 +5。
- 不能對同一目標無限吸。
- 應與怪物／目標的 MP 或可吸額度相關。
- 吸取數值應有 Server 決定的隨機變化。
- 必須建立在 Server-confirmed actual damage / legal hit 之後。

完整公式與正式內容日後再討論。

## 九、後續 combat / encounter 系統

### 單一 incoming-damage pipeline

盾牌 v1 將 entity damage 收斂到共用 defensive resolution；後續新增 resistance、status、proc 時也必須沿用同一 owner path，不得讓 melee、ranged、monster、skill 各自複製防禦公式。

目前鎖定的核心順序：

```text
合法傷害來源
-> DamageType / Blockable 等 Server semantics
-> authoritative equipment / defense resolution
-> PhysicalDefense 或 MagicReduction
-> block roll（只有明確 Blockable 時）
-> 最後一次 rounding / minimum damage
-> final damage
-> HP mutation
-> CombatEvent / contribution / presentation event
```

未來 proc / status 的插入順序需在新增該系統時明確定義，但不能繞過 final authoritative damage owner path。

### Threat table

從目前 retaliation 逐步升級：

- stable `EntityID` / character identity
- actual damage contribution
- target invalidation / fallback
- death / disconnect cleanup
- evade / encounter reset cleanup
- pack assist 走 AI policy

Threat 與 loot contribution 可以共用「Server 確認的實際傷害事實」，但兩者不能共用同一份 gameplay table。

### Status / buff / debuff

未來 poison、slow、stun、temporary shield、weapon enchant、resistance 等應走通用 effect lifecycle：

- stable effect ID
- source / target
- authoritative start / end tick
- stack / refresh policy
- apply / revert 成對
- persistence policy

### Monster abilities

做通用能力系統後才逐隻怪物配置：

- cast range / LOS
- cooldown
- target selector
- HP threshold
- direct / area damage
- heal
- buff / debuff
- poison
- summon

具體 monster / skill 內容必須先討論。

## 十、物品、經濟與多人內容 roadmap

### Item instance

未來若加入：

- durability
- enchant
- binding
- tradable state
- instance roll

則 drop / pickup / persistence / warehouse / trade 全部必須完整保留同一 item instance state。

### Economy transaction

- shop preflight / atomicity
- warehouse integrity
- player trade escrow
- confirmation reset
- cancel restore
- crash recovery
- idempotency

### Party

- invite / accept / leave / leader
- stable member identity
- vitals presentation
- loot policy
- cooperative threat semantics

### Quest

以 Server authoritative event 更新 objective：

- kill
- pickup
- interact
- enter-area

reward 不可因 reconnect / retry 重複發放。

## 十一、參考 `myriad-throne-server` 的原則

可參考的是成熟 MMORPG 的 invariant 與 regression tests，不是其內容或舊架構。

值得借鑑：

- 共用 damage resolution
- equipment eligibility / derived state 集中管理
- legality 先於 gameplay mutation
- combat queue reentrancy 與 failure-path regression tests
- status apply / revert lifecycle
- threat consistency
- transaction rollback / failure tests
- persistence snapshot / journal correctness
- visibility / AOI isolation

禁止照搬：

- 具體武器／技能／職業／怪物／掉落
- L1 protocol / compatibility
- Client gfx ID
- session identity 當 gameplay identity
- 舊 class hardcode
- 為了參考專案而改成 Lua-first gameplay architecture
