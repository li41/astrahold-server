## 工作分類原則

- **可直接做**：不需要新增產品語義，且能以現有 Server authority／contract 判定正確性。
- **等待 Client**：Server contract 已存在，剩餘工作由正式 Client 消費、呈現或回報 integration requirement。
- **待討論**：會新增 gameplay、成長、經濟、取得方式、數值或新 Protocol semantics；沒有明確決策前 Server 不猜。
- **暫不規劃**：目前不是 Server-first 工作；不以 infrastructure-first／framework-first／content-churn 填空。

## 待產品／使用者決策

以下項目已有部分 foundation，但 **不能因底層已有 helper 就自行升格成產品行為**。

### 1. 角色成長與屬性點 mutation

已定方向：六大基礎屬性、中性基準 10、創角額外 10 點、創角單項最多 +5、51 級後每級 +1 點。

仍需決定：

- 正式 character level／progression owner 與既有角色資料如何對接。
- 創角配點的 Client intent／確認／重送／失敗語義。
- 51 級後點數取得與消耗的 authoritative mutation contract。
- 是否允許重置、成本／限制／安全邊界。

未定前不得建立第二套 level truth。

### 2. 技能取得／學習與六格編輯

已有 20 技能穩定 ID、learned-skill authoritative state、6 格 combat loadout 與 durable persistence。

仍需決定：

- 技能如何取得／學習；是否有等級、物品、NPC、任務或其他條件。
- 是否可忘卻／重學／重置，以及成本與限制。
- 六格何時可編輯、是否可在戰鬥中改、Client intent 與 Server rejection semantics。

### 3. 尚未定案的技能效果／數值

至少包含：

## 地圖／場景 — Client 主導，Server 暫不先規劃

這是正式工作邊界：

- 地圖、場景 layout、視覺動線、場景資產與 playable-space 迭代由正式 Three.js Client 主導。
- gpt-server **不預先規劃下一張地圖、新手村重做、城牆、入口、portal、siege gate、blocker 數量或 spawn layout**。
- Client 做到一個需要 gameplay authority 的具體 slice 後，再透過 integration Issue／comment 回饋 Server。
- Server 只針對該具體需求定義與實作必要的 authoritative facts，例如碰撞／可通行區域、傳送、出生、互動區域、AI 區域或 siege legality；不從 Client asset path／scene node／raycast 自動推導 gameplay truth。
- 現有 `worlds/castle-sandbox/gameplay.json` 只是目前 Server 已存在的 gameplay config／相容基準，不代表 Server 主動規劃未來地圖的 roadmap。

因此「做下一張地圖／重做 Emberwatch／新增攻城入口」**不列入 Server 待辦**，直到 Client 提供明確 handoff。

## P1／P2 — 有正式產品需求再排程

- 正式怪物能力與 slow／stun／poison／buff／debuff／summon 等效果：先有技能／怪物契約再做。
- 經濟交易、隊伍、任務：在核心角色／裝備／技能 loop 有明確產品需求後再進場。
- 寵物、郵件、私人商店、拍賣、製作、公會、戰爭、攻城、排行、釣魚、房屋：目前不排 Server-first 施工。

每次選下一個 Server slice 仍以：

**玩家可見、可玩的結果 > Server authority > 商用品質 > AI 可維護性 > 可測試性與授權安全**

為優先順序。
