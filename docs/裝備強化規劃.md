# 星壘 — 裝備強化規劃

本文件是 Astrahold 正式 Server 的裝備強化 gameplay 規格。強化 outcome、卷軸消耗、裝備等級變更、裝備銷毀、持久化與 Protocol 語義全部由 Server authoritative path 決定；Client 只送 intent 並呈現 Server result／snapshot，不得 optimistic mutation。

## 一、正式卷軸 identity

本輪只使用已存在的穩定 `ItemArchetypeID`：

- 武器強化卷軸：`item_astrahold_weapon_enhancement_scroll`
- 防具強化卷軸：`item_astrahold_armor_enhancement_scroll`

武器卷軸只可用於 `weapon`；防具卷軸可用於 `armor` 與 `shield`。

舊專案另有祝福／詛咒卷軸的跳級／降級規則，但 Astrahold 目前尚未定義對應 stable item identity；本規格不自行發明第三、第四種卷軸 archetype。

## 二、安全強化值

正式安全值：

- 武器：**+6**
- 防具：**+4**
- 盾牌：**+4**

當目前強化等級低於安全值時，每次合法強化：

- 成功率 100%
- 成功固定 +1
- 無變化 0%
- 爆裝 0%
- 消耗 1 張對應卷軸

因此武器 `+0 -> +6` 全部必成；防具與盾牌 `+0 -> +4` 全部必成。

## 五、沒有 gameplay 最高上限

**裝備強化不設 gameplay 最高等級。**

- 不存在 `+10`、`+12` 或其他「到頂後拒絕」規則。
- 尾段仍以固定 1% 成功率持續向上。
- Server 不得因達到某個產品層級而回傳 `at_limit`。
- 程式資料型別若存在有限表示範圍，只是技術儲存邊界，不得被描述成 gameplay 設計上限；若接近表示邊界，應以資料 migration／型別擴充處理，而不是把它變成遊戲規則。

## 六、每次合法強化的 outcome

每次已通過 Server 驗證的強化嘗試都先消耗 **1 張卷軸**，再套用 Server 決定的結果：

1. `enhanced`
   - 目標裝備保留同一個 `ItemInstanceID`。
   - `EnhancementLevel += 1`。
   - authoritative inventory/equipment snapshot 反映新等級。
2. `nochange`
   - 卷軸已消耗。
   - 裝備保留。
   - `EnhancementLevel` 不變。
3. `broken`
   - 卷軸已消耗。
   - 目標 `ItemInstance` 從 authoritative inventory／equipment state 移除。
   - 若目標當時已裝備，對應 equipment slot 同步清空；後續戰鬥屬性必須從新的 authoritative equipped state 重算。

只有 intent 本身不合法、找不到卷軸、找不到目標、卷軸類型不相容、角色狀態禁止操作或 Server invariant 失敗等情況才是 `rejected`；rejected 不消耗卷軸。

## 七、亂數與權威邊界

- 機率判定只能在 Server world-owner gameplay mutation path 執行。
- Client 不傳 roll、不傳成功率、不傳目標結果。
- 同一個 reliable `ClientActionSequence` 只能處理一次；duplicate/replay 不得再次消耗卷軸或再次擲骰。
- 測試必須可注入／控制 roll，使成功、無變化、爆裝與邊界機率都能 deterministic 驗證。
- world tick 不做 blocking I/O；強化 persistence 依既有 inventory/equipment dirty-save 流程處理。

## 八、戰鬥屬性效果

目前 Astrahold V1 已採：

- 武器 `+N` -> equipped `PhysicalDamage +N`
- 防具／盾牌 `+N` -> equipped `PhysicalDefense +N`

這些加成必須從 authoritative equipped `ItemInstance.EnhancementLevel` 即時計算，不能另存第二份 mutable enhancement bonus truth。

## 九、Protocol／Client 原則

現行強化 intent/result contract 使用 Protocol v30 Type 123/124；這個 slice 在正式 Client handoff 前仍可調整 v30 的 outcome enum，使其正確表達 `enhanced / nochange / broken / rejected`。

Client 必須：

- 只送卷軸 archetype 與目標 `ItemInstanceID`。
- 不自行扣卷軸。
- 不自行增加強化值。
- 不自行銷毀爆掉的裝備。
- 以 Server result 與後續 authoritative inventory/equipment snapshot 為最終 truth。
- reconnect/relogin 後以 Server durable state 還原 `EnhancementLevel`，不得依本地歷史推算。

## 十、驗證最低要求

實作完成後至少驗證：

- 武器 +0..+5 必成；+6 開始使用風險表。
- 防具／盾牌 +0..+3 必成；+4 開始使用風險表。
- 每一階 success／nochange／break 百分比邊界正確。
- 武器 `>= +12` 與防具／盾牌 `>= +10` 固定 1/39/60，且仍可成功繼續 +1。
- 無 `at_limit` gameplay rejection。
- nochange 消耗一次卷軸但保留裝備與等級。
- broken 消耗一次卷軸並刪除 exact target instance；已裝備目標會同步清 slot。
- duplicate action sequence 不會重複消耗、擲骰或銷毀。
- 成功後的 +N 戰鬥屬性立即生效。
- snapshot／persistence／reconnect 保留成功強化等級並正確反映爆裝後不存在的 instance。
