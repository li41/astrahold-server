# 星壘 Astrahold — 規劃總覽

本文件是 **目前完整規劃的唯一閱讀入口**。如果只想知道「現在做到哪、下一步做什麼、哪些內容已定、哪些還沒定」，從這裡開始。

會隨開發快速變動的 Protocol、PR、exact head、blocker 與驗證結果，以 [專案狀態](專案狀態.md) 為準；本文件保存較穩定的 gameplay roadmap、系統優先順序與 backlog 脈絡。

## 固定 gameplay authority

```text
Client Intent
-> Go Server Validate / Decide
-> Authoritative State / Events
-> Client Presentation
```

Server 是唯一 gameplay truth。Client 的動畫、VFX、UI、camera、prediction、root motion、raycast、smoothing 都不能決定 gameplay outcome。

## 現在的可玩主線

目前優先把 MMORPG 基本循環做成值得玩的產品：

```text
移動
-> 選怪
-> 攻擊 / 被攻擊
-> HP / MP / cooldown
-> 死亡 / 重生
-> 擊殺
-> 掉落
-> 撿取
-> 背包
-> 使用物品
-> 裝備
-> 持久化
```

大型公會、拍賣、製作、攻城等系統保留在後續，不提前壓過目前 PvE / 裝備 / 戰鬥品質。

## 目前最重要的內容狀態

### 低階裝備 v1

低階主手／副手、武器攻擊資料、盾牌 mitigation 與裝備持久化已經進入正式 Server gameplay stack。歷史實作來源可從舊 PR 查考，但不再以舊 feature branch 作為目前工作入口。

目前已具備：

- 3 把劍
- 1 把斧
- 1 把錘
- 3 面盾牌
- 正式 `MainHand` / `OffHand`
- 武器體型傷害資料
- 盾牌物防／格擋／魔法減傷資料
- 主手＋副手持久化

但以下仍 **沒有正式取得方式**：

- 無怪物掉落
- 無掉率
- 無商店
- 無材料兌換
- 無任務
- 無製作
- 無初始裝備
- 無金幣價格

任何 agent 都不能自行補完這些內容。

### 盾牌 v1 已定案並完成 Server 驗證

物理防禦：

```text
PhysicalMitigationRate = PhysicalDefense / (PhysicalDefense + 20)
```

傷害流程：

```text
合法傷害
-> DamageType / Blockable
-> authoritative OffHand
-> PhysicalDefense 或 MagicReduction
-> 若明確 Blockable，Server 擲一次 BlockChance
-> 成功才套 BlockReduction
-> 最後四捨五入一次
-> 一般正傷害最低 1
-> authoritative final damage
```

已確認：

- `DamageType` 與 `Blockable` 分離；Physical 不代表一定可格擋。
- `basic-attack`、`wolf-bite`：Physical + Blockable。
- `shatter-strike`：Physical + NotBlockable。
- `fireball`、`meteor-strike`：Magic + NotBlockable。
- 方紋魔盾提供 8% MagicReduction；Magic 不擲盾牌 BlockChance。
- v1 不看角色面向或攻擊角度。
- 低階盾牌所有職業都能使用，資料明確為 `ClassPolicy=All`。
- 未來限制裝備使用 `AllowList + stable ClassID`；Server 沒有 authoritative ClassID 時 fail closed。
- Client 不計算 mitigation、不擲 block，只呈現 Server final damage / blocked result。

詳細數值與平均減傷見 [遊戲內容與系統規劃](遊戲內容與系統規劃.md)。Client 的目前 integration 狀態不要從舊 v24 敘述判定，改讀 [專案狀態](專案狀態.md)。

### Encounter threat v1 已完成 Server 驗證

Server 已將原本「靠近後鎖住單一目標」升級成 actual-damage-driven threat fallback：

```text
初始 proximity acquire 最近合法玩家
-> 玩家造成 Server-confirmed actual damage
-> 獨立 threat table 累加
-> 最高 threat 成為目前 AI target
-> invalid target prune
-> fallback 下一個 threatened target
-> 全部失效才 evade / return home
```

已確認：

- Threat 使用 stable `EntityID`，SessionID 只做 source ownership驗證。
- Threat 增量就是 Server-confirmed actual damage。
- 同 threat 以較小 `EntityID` 穩定決勝。
- dead / disconnect / revive protection / wrong layer / leash / LOS 都會使 target 失效並被 prune。
- disconnect 後即使 world entity 暫時仍存在，也不能繼續當合法 AI target。
- evade、monster defeat/despawn/respawn 都清空 encounter threat。
- Threat 與 loot contribution 共用 actual-damage fact，但絕不共用同一張 gameplay table。
- Threat 目前是純 Server AI truth，沒有 Client-side threat authority。

### Public ground-drop expiry 已完成

Public monster ground drop 已有 bounded Server-owned lifetime：

- expiry 使用 authoritative tick deadline，而不是 wall-clock timer。
- 由單一 world-owner lifecycle stage 處理。
- pickup / auto-loot / rollback removal 會清除 expiry bookkeeping，不做 double mutation。
- expiry 走既有 authoritative world removal；Client 消費正常 `EntityDespawn`。
- deadline arithmetic 必須避免 wrap。

目前 exact head 與 CI 證據見 [專案狀態](專案狀態.md)。

### Transient Status lifecycle 第一階段已完成

第一個正式案例使用既有 Oathguard Fortify，不新增技能數值、不改 Protocol：

- Server-owned stable EffectID + EntityID status store。
- apply / refresh / half-open expiry / remove / entity clear。
- Fortify 的 3 秒、45% self mitigation 結果不變。
- player defeat / formal leave / monster defeat 會清空該 Entity incarnation 的 transient combat status。
- monster respawn 即使重用 EntityID，也不得繼承舊 incarnation status。

這是 lifecycle foundation，不代表 Weakpoint、裂甲、slow、stun、poison 等歷史設計已自動成為正式 gameplay。下一個具體 status 仍必須先有 current formal contract。exact head 與 CI 證據見 [專案狀態](專案狀態.md)。

### 吸魔武器

歷史技術原型只視為 implementation evidence，**不是正式內容規格**。

已撤回：

- 固定 `+5 MP`
- `3 灰狼皮 -> 吸魔法杖`
- 任何未經討論的正式取得方式

正式方向只保留：

- 不能固定 +5。
- 不能對同一目標無限吸。
- 應與目標 MP／可吸額度相關。
- 吸取量應有隨機變化。

完整公式之後再討論。

## 近期 Server roadmap

### P0 — 盾牌真正進入戰鬥：Server 已完成

- 單一 authoritative incoming-damage pipeline。
- 盾牌 PhysicalDefense、BlockChance、BlockReduction、MagicReduction。
- 同一筆 HP mutation、CombatEvent、loot contribution 以同一 Server final damage resolution 為基礎。
- 格擋成功結果由 Server event 提供給 Client 做動畫／VFX／音效。
- 裝備效果從 authoritative equipment state 即時解析，不把 presentation 或 Client 狀態變成 gameplay truth。

### P0 — Encounter / threat consistency：Server 已完成 v1

- 通用 threat table。
- actual damage accumulation。
- highest-threat selection。
- invalid target prune / fallback。
- death / disconnect / evade / lifecycle reset correctness。
- threat 與 loot contribution 分離。

未來 taunt、heal threat、party threat、pack assist 只有在實際玩法需要時再加入 generic policy，不先做 framework。

### P0 — Public ground-drop expiry：Server 已完成

- public ground drop 有 bounded Server-owned lifetime。
- world-owner tick lifecycle。
- pickup / auto-loot / rollback cleanup。
- normal authoritative `EntityDespawn`。
- 不新增 Client-side expiry authority。

### P0 correctness gate — Tick / action reentrancy

current v27 的既有玩家 action producer 仍在 world-owner command dispatch 內同步 prepare → resolve；目前沒有獨立的反擊、proc、死亡 callback 等巢狀 action producer，因此**不為尚不存在的 producer 預先建立 reentrancy framework**。

此項改為未來 correctness gate：

- 一旦新增反擊、proc、死亡 callback 或其他可在 action resolution 中產生新 action 的機制，必須先明確定義 same-tick / next-tick ordering。
- 必須有 focused exactly-once tests，避免 queue 清理、callback 或 lifecycle stage 造成 action 遺失／重複。
- nested action 仍只能由 authoritative world-owner path mutation，不得由 Network、DB、Client 或 presentation callback 直接改 gameplay truth。

### P1 — Status / Buff / Debuff：第一階段已完成

目前已完成最小通用 transient lifecycle，並以正式 Fortify 驗證 gameplay 使用路徑。

後續原則：

- 下一個具體 status 只從**已有正式技能／contract 語義**中選擇。
- stack / refresh / derived-state policy 只實作正式內容真正需要的語義，不先做萬用 framework。
- 需要跨重連的狀態才進 durable persistence。
- poison、slow、stun、temporary resistance、weapon enchant 等只代表可擴充方向；未有正式數值／技能語義者不得自行補完。
- recovered Weakpoint、裂甲等歷史 balance 值不能因 lifecycle 已存在就自動升格成 production gameplay truth。

### P1 — Monster abilities

先做通用能力規格，再只加入少量真的改善 PvE 的怪物能力：

- range / LOS
- cooldown
- target selector
- HP threshold
- direct / area damage
- heal / buff / debuff / poison / summon

具體怪物與技能內容仍要先有正式內容決策，不從歷史草稿自行恢復。

### P1 — Ground effects / traps / hazards

Server 決定觸發、範圍、傷害、TTL 與 entity lifecycle；Client 只呈現。具體技能／陷阱內容仍需有正式 contract 才落地。

### P1 — Item instance 完整性

未來若加入耐久、強化、綁定、可交易狀態，drop / pickup / persistence / trade 都必須完整保存同一 item instance truth。

### P2 — Economy transaction correctness

- NPC shop 原子性
- warehouse
- player trade escrow / confirm / cancel restore
- crash recovery / idempotency
- disconnect / shutdown cleanup

### P2 — Party / cooperative PvE

- invite / accept / leave / leader
- party identity / vitals
- loot policy
- 多人 threat / contribution 語義

### P2 — Quest / world progression

以 authoritative event 驅動 objective：kill、pickup、interact、enter-area；reward grant 與 inventory / currency transaction 共用 correctness 規則。

### P3 — 後期參考 backlog

- pet / summon
- mail
- private shop
- auction
- crafting
- guild / clan
- war
- castle / siege
- ranking
- fishing
- housing

這些是參考 backlog，不代表近期施工順序。

## 產品呈現方向

從舊 Assets 視覺規劃中保留的有效方向：

- 暗色邊境奇幻、但不能黑到看不清 gameplay。
- 2.5D / 俯視 gameplay camera 下必須有清楚 silhouette。
- 玩家、NPC、怪物、掉落物在遊玩距離一眼可辨識。
- 場景要像 MMORPG 地點，不像 debug arena。
- target、attack started、hit、defeated、loot spawned 五個狀態必須明確。
- 繁中 UI 為第一優先語系。
- VFX / audio 由 Server authoritative state / event 觸發；不得反過來決定 gameplay。
- 採 `$0-first`：先用已合法取得或 Astrahold 原創素材證明呈現流程，只有具體瓶頸存在時才購買。

舊 Unreal-only 的 UMG、Niagara、Lumen、Paragon、Manny/Quinn 等實作細節已不再視為現行規劃；正式 Client 現在是 Three.js。

## 參考專案使用原則

`li41/myriad-throne-server` 可只讀參考成熟 MMORPG 行為與 regression tests。

可借鑑：

- 單一 damage rule 入口
- threat / aggro consistency / highest-threat fallback
- equipment derived-state rebuild
- status lifecycle
- transaction failure tests
- persistence snapshot / journal correctness
- action queue reentrancy
- visibility / AOI 邊界
- stable identity

不可照搬：

- L1 Protocol / 舊 Client 相容層
- Lua 驅動全部 gameplay 規則
- session-based gameplay identity
- 內容數值、掉落、職業、技能、怪物
- Client gfx / asset ID

## 每次選下一個 Server slice 的判斷

**「玩家現在能多看到什麼、玩到什麼、感受到什麼？」**

優先順序固定：

**玩家可見、可玩的結果 > Server authority > 商用品質 > AI 可維護性 > 可測試性與授權安全**
