## 固定 gameplay authority

```text
Client Intent
-> Go Server Validate / Decide
-> Authoritative State / Events
-> Client Presentation
```

Server 是唯一 gameplay truth。Client 的動畫、VFX、UI、camera、prediction、root motion、raycast、smoothing 都不能決定 gameplay outcome。

## 現在的可玩主線

目前優先把 MMORPG 基本循環做成值得玩的產品：

```text
移動
-> 選怪
-> 攻擊 / 被攻擊
-> HP / MP / cooldown
-> 死亡 / 重生
-> 擊殺
-> 掉落
-> 撿取
-> 背包
-> 使用物品
-> 裝備
-> 持久化
```

大型公會、拍賣、製作、攻城等系統保留在後續，不提前壓過目前 PvE / 裝備 / 戰鬥品質。

## 目前最重要的內容狀態

### 低階裝備 v1

已定義並在 Server PR #149 實作／驗證：

- 3 把劍
- 1 把斧
- 1 把錘
- 3 面盾牌
- 正式 `MainHand` / `OffHand`
- 武器體型傷害資料
- 盾牌物防／格擋／魔法減傷資料
- 主手＋副手持久化

但以下仍 **沒有取得方式**：

- 無怪物掉落
- 無掉率
- 無商店
- 無材料兌換
- 無任務
- 無製作
- 無初始裝備
- 無金幣價格

任何 agent 都不能自行補完這些內容。

### 盾牌 v1 已定案

物理防禦：

```text
PhysicalMitigationRate = PhysicalDefense / (PhysicalDefense + 20)
```

傷害流程：

```text
合法傷害
-> DamageType / Blockable
-> authoritative OffHand
-> PhysicalDefense 或 MagicReduction
-> 若明確 Blockable，Server 擲一次 BlockChance
-> 成功才套 BlockReduction
-> 最後四捨五入一次
-> 一般正傷害最低 1
-> authoritative final damage
```

已確認：

- `DamageType` 與 `Blockable` 分離；Physical 不代表一定可格擋。
- `basic-attack`、`wolf-bite`：Physical + Blockable。
- `shatter-strike`：Physical + NotBlockable。
- `fireball`、`meteor-strike`：Magic + NotBlockable。
- 方紋魔盾提供 8% MagicReduction；Magic 不擲盾牌 BlockChance。
- v1 不看角色面向或攻擊角度。
- 低階盾牌所有職業都能使用，資料明確為 `ClassPolicy=All`。
- 未來限制裝備使用 `AllowList + stable ClassID`；Server 沒有 authoritative ClassID 時 fail closed。
- Client 不計算 mitigation、不擲 block，只呈現 Server final damage / blocked result。

詳細數值與平均減傷見 [遊戲內容與系統規劃](遊戲內容與系統規劃.md)。v1 先以這套數值實測，有問題再依遊玩結果調整。

### 吸魔武器

PR #148 只視為技術原型，**不是正式內容規格**。

已撤回：

- 固定 `+5 MP`
- `3 灰狼皮 -> 吸魔法杖`
- 任何未經討論的正式取得方式

正式方向只保留：

- 不能固定 +5。
- 不能對同一目標無限吸。
- 應與目標 MP／可吸額度相關。
- 吸取量應有隨機變化。

完整公式之後再討論。

## 近期 Server roadmap

### P0 — 盾牌真正進入戰鬥

玩家換盾後要真的感受到差異，而不是只看到裝備欄變化。

已鎖定並進入實作／驗證：

- 單一 authoritative incoming-damage pipeline。
- 盾牌 PhysicalDefense、BlockChance、BlockReduction、MagicReduction。
- 同一筆 HP mutation、CombatEvent、loot contribution 以同一 Server final damage resolution 為基礎。
- 格擋成功結果由 Server event 提供給 Client 做動畫／VFX／音效。
- 裝備效果從 authoritative equipment state 即時解析，不把 presentation 或 Client 狀態變成 gameplay truth。

### P0 — Encounter / threat consistency

- 從目前 retaliation 擴成真正 threat table。
- 使用 stable `EntityID` / character identity。
- 目標死亡、斷線、evade、reset 都要正確清理／重選。
- damage contribution 與 threat 共用「實際傷害事實」，但不能綁成同一張表。

### P0 — Tick / action reentrancy correctness

- 反擊、proc、死亡 callback、同 tick 新 action 必須有明確 ordering。
- focused tests 鎖住 exactly-once，避免 queue 清理時遺失或重複。

### P1 — Status / Buff / Debuff

- poison、slow、stun、temporary resistance、weapon enchant 等走通用 effect lifecycle。
- apply / expiry / remove / restore 成對。
- 需要跨重連的狀態才進 durable persistence。

### P1 — Monster abilities

先做通用能力規格，再只加入少量真的改善 PvE 的怪物能力：

- range / LOS
- cooldown
- target selector
- HP threshold
- direct / area damage
- heal / buff / debuff / poison / summon

具體怪物與技能內容仍要先和使用者討論。

### P1 — Ground effects / traps / hazards

Server 決定觸發、範圍、傷害、TTL 與 entity lifecycle；Client 只呈現。

### P1 — Item instance 完整性

未來若加入耐久、強化、綁定、可交易狀態，drop / pickup / persistence / trade 都必須完整保存同一 item instance truth。

### P2 — Economy transaction correctness

- NPC shop 原子性
- warehouse
- player trade escrow / confirm / cancel restore
- crash recovery / idempotency
- disconnect / shutdown cleanup

### P2 — Party / cooperative PvE

- invite / accept / leave / leader
- party identity / vitals
- loot policy
- 多人 threat / contribution 語義

### P2 — Quest / world progression

以 authoritative event 驅動 objective：kill、pickup、interact、enter-area；reward grant 與 inventory / currency transaction 共用 correctness 規則。

### P3 — 後期參考 backlog

- pet / summon
- mail
- private shop
- auction
- crafting
- guild / clan
- war
- castle / siege
- ranking
- fishing
- housing

這些是參考 backlog，不代表近期施工順序。

## 產品呈現方向

從舊 Assets 視覺規劃中保留的有效方向：

- 暗色邊境奇幻、但不能黑到看不清 gameplay。
- 2.5D / 俯視 gameplay camera 下必須有清楚 silhouette。
- 玩家、NPC、怪物、掉落物在遊玩距離一眼可辨識。
- 場景要像 MMORPG 地點，不像 debug arena。
- target、attack started、hit、defeated、loot spawned 五個狀態必須明確。
- 繁中 UI 為第一優先語系。
- VFX / audio 由 Server authoritative state / event 觸發；不得反過來決定 gameplay。
- 採 `$0-first`：先用已合法取得或 Astrahold 原創素材證明呈現流程，只有具體瓶頸存在時才購買。

舊 Unreal-only 的 UMG、Niagara、Lumen、Paragon、Manny/Quinn 等實作細節已不再視為現行規劃；正式 Client 現在是 Three.js。

## 參考專案使用原則

`li41/myriad-throne-server` 可只讀參考成熟 MMORPG 行為與 regression tests。

可借鑑：

- 單一 damage rule 入口
- threat / aggro consistency
- equipment derived-state rebuild
- status lifecycle
- transaction failure tests
- persistence snapshot / journal correctness
- action queue reentrancy
- visibility / AOI 邊界
- stable identity

不可照搬：

- L1 Protocol / 舊 Client 相容層
- Lua 驅動全部 gameplay 規則
- session-based gameplay identity
- 內容數值、掉落、職業、技能、怪物
- Client gfx / asset ID

## 每次選下一個 Server slice 的判斷

**「玩家現在能多看到什麼、玩到什麼、感受到什麼？」**

優先順序固定：

**玩家可見、可玩的結果 > Server authority > 商用品質 > AI 可維護性 > 可測試性與授權安全**
